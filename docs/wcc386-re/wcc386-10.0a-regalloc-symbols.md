# wcc386 10.0a register-allocator symbol map (recovered from a live dump)

> Tooling paths below (`qemu-harness/`, `scripts/dump_analyze.py`,
> `tools/patch_trace.py`) are in the sibling
> `~/git/ReverseEngineering/watcom10.0a` repo — see `README.md` “Where the
> tooling lives”.

Recovered by running the real `wcc386.exe` under the QEMU/FreeDOS harness
(`qemu-harness/`), setting a gdb read-watchpoint on the `DoubleRegs` table,
enumerating every function that reads it, and walking the call graph in the
*relocated* live image (`scripts/dump_analyze.py`).  This defeats the static-RE
wall (README §5b: table pointers are load-time relocated, absent from the file).

## Address spaces (this build / capture)

```
file offset F  ->  app-offset O (= disp32 the code uses)  ->  linear 0x10000000+O  ->  physical
```
* wcc386 runs flat, **CS/DS/SS base = 0x10000000**, CPL=3, paging on (CR3 0x11000).
* `file = app-offset + 0x1200`  (e.g. DoubleRegs app-offset 0x7A850 = file 0x7BA50).
* All offsets below are **app-offsets**; linear = `0x10000000 + offset`.  These
  are stable across boots (no ASLR in DOS/TNT), so they're valid breakpoint
  targets: `break *0x10000000+<offset>`.

## Functions (the allocator call chain)

| app-offset | name (OW-equiv) | role |
|-----------:|-----------------|------|
| `0x57b78` | **`GiveBestReg(conflict, tree, except, needs_one)`** | picks the register; iterates `tree->regs`, scores candidates (CountRegMoves), then calls `FixInstructions` to APPLY the pick.  (Verified in Ghidra; prologue `sub esp,0x20`.) |
| `0x56f64` | **`FixInstructions(conf, tree, reg, need_live_update)`** | APPLIES register `reg` (3rd arg = EBX in __watcall) to the conflict's instruction range.  Frame `sub esp,0x34`.  **NB:** an earlier table wrongly labelled this `0x57F64`/`GiveBestReg` (a call-level off); the chosen register is its `reg` arg, and `conf->with.regs` still holds the interference mask at its entry. |
| `0x57ed8` | **`GiveRegister(conflict=eax)`** | builds `conflict->tree`, then `GiveBestReg`, then frees the tree. |
| `0x563FC` / `0x563C0` | tree orchestrators | build `conflict->tree` (`[conflict+0x10]`); call the builders below. |
| `0x561E3` | **`BuildRegTree`** | recursive (self-calls `0x561ED`/`0x561F5`); copies `RegLists[class]` → `tree->regs`. |
| `0x55F92` | `SimpleTree` | alloc tree node, `tree->class = conflict->type_class`, call `BuildRegTree`, store `conflict->tree`. |
| `0x55FC4` | complex tree builder | conflict-aware tree construction. |
| `0x3F004` | **`RegClass(reg)`** | register → class index; scans `RegLists[0..9]` via byte class-table `0x7AAC9`. |
| `0x3F040` | `RegClass` wrapper | special cases (class 9 for `0x10000`, scan `0x7A8D4` for class 0xA). |
| `0x3F32B` | `&DoubleRegs` accessor | `mov eax,0x7A850; ret` (int alloc-order list getter). |

## Struct offsets

`conflict_node`: `+0x08` ins/value · `+0x10` tree · `+0x56` type_class (byte).
`reg_tree node`: `+0x10` regs (candidate array, copied from the list) · `+0x20` class (byte).

## Slot-assignment pipeline (AssignTemps / Names[N_TEMP] sort)

A SEPARATE pipeline from the register-conflict sort above.  These are the
sites for the stack-SLOT ORDER of spilled locals (Rule 107).  Verified in
the binary via pyghidra; full canon: `docs/slot-swap-survey-2026-06-25.md`.

| app-offset | name | role |
|-----------:|------|------|
| `0x55463` | **`AssignTemps`** | late in `Generate`: sorts `Names[N_TEMP]` then `AllocNewLocal`-walks the NEEDS_MEMORY/!HAS_MEMORY/!ALIAS subset. |
| `0x590ab` | **`BuildNameConflicts`** | earlier; its terminal `SortList` is the FIRST Names-list sort (input = nb1 declaration order). |
| `0x55503` | **`SortCmp_flag2_2b`** (OW v1 `TempAllocBefore`) | the AssignTemps Names-list comparator. Keys: ALIAS bit byte`[+0x2b]`&0x2 → `n.size` `[+0x8]` → `[+0x24]` (sort-equal if DIFFERS) → `[+0x10]` `v.offset` DESC. |
| `0x5905b` | **`AllocBefore`** | the BuildNameConflicts Names-list comparator. Keys: CONST_TEMP bit byte`[+0x2b]`&0x1 → has-conflict `[+0xc]` → savings DESC (both-conflict) → `[+0x24]` DESC (both-no-conflict). |
| `0x66708` | **`SortList`** | list-sort dispatch (generic). |
| `0x665c4` | **`DoSortList`** | back-end of SortList: alloc-SUCCESS arm → `ShellSort` (UNSTABLE); alloc-FAILURE arm → `MergeList` @0x66566 (stable). Normal lists take the unstable arm. |
| `0x66689` | **`ShellSort`** | the (non-stable) shell sort: `gap=length; do{adj=!adj; gap=gap/2+adj; bubble-to-fixed-point on before(a[i+gap],a[i])}while(gap!=1)`. |
| `0x66532` | **`BuildList`** | rebuild the linked list from the sorted pointer array (order-preserving). |
| `0x66566` | **`MergeList`** | stable merge sort fallback (alloc-failure path only). |
| `0x558d4` | **`AllocNewLocal`** | per-temp slot allocator: `CalcRange` + `ReUsableStack` (else fresh); calls `SetTempLocation` for a fresh slot, or reuses an existing offset (no SetTempLocation). |
| `0x5561e` | **`ReUsableStack`** | coalesces a temp into an existing slot iff instruction-ID ranges don't overlap. |
| `0x4e6bb` | **`SetTempLocation`** | the GROUND-TRUTH slot commit: `locals.size += size; temp->t.location = -locals.size - locals.base`. First call → highest `[esp+N]`. |

`[+0x24]` (read by both comparators) is a per-temp id = **reverse-declaration-rank**, assigned by the front-end at decl time.  Offline simulator: `c2/regalloc/shellsort_sim_slots.py`.

## How to dump a real allocation decision

```
break *0x10000000+0x57b78          # GiveBestReg entry (the real selection fn)
# eax = conflict, edx = tree.  Read:
#   tree->regs  = *(int*)(0x10000000 + edx + 0x10)   -> candidate list base
#   conflict->type_class = *(char*)(0x10000000 + eax + 0x56)
break *0x10000000+0x56f64          # FixInstructions entry (applies the pick)
# the chosen register is the 3rd arg = EBX here; conf->with.regs (eax+0x20)
# still holds the interference mask.  (This is the address an earlier note
# mislabelled 0x57f64/GiveBestReg.)
```
In practice the container `-trace` image (tools/patch_trace.py) captures all of
this on stdout (`al`/`rg`/`wr`/`gi`) -- no debugger -- which is why the QEMU/gdb
harness was retired.

## `c2 regtrace <function>` — the workflow command

`c2 regtrace <fn>` makes this usable for the decomp grind:

1. extracts the single function (preamble + body, via the `// FUNCTION:`/`STUB:`
   annotation boundaries) into a one-function TU;
2. stages it + the project headers on the B: floppy (≈210 KB, fits 1.44 MB —
   reuses the proven C:-IDE-toolchain + B:-floppy device config);
3. runs the harness, breakpoints `GiveBestReg`, dumps every decision (class +
   candidate `DoubleRegs`-order list + the availability flag globals) to
   `work/regtrace.json`;
4. prints it next to PS.EXE's disassembly + the registers PS actually uses.

```bash
uv run c2 regtrace barbarian_in_region          # trace + PS context
uv run c2 regtrace move_army --file int_c2.c     # disambiguate
uv run c2 regtrace foo --json                    # raw JSON
```

**Intended use** (not random permuting): point it at a *representative of an
unexplained regalloc cluster* (functions `regalloc_explain` marks "outside the
model" / no rule hint).  The live `GiveBestReg` candidate order + the flag
globals it read reveal *why* our register choice diverges from PS, which becomes
a new entry in `docs/watcom-codegen-patterns.md` that then closes the whole
cluster.

**RESOLVED (2026-06-01) — two root-cause fixes in the QEMU path.**  The earlier
`Cannot insert breakpoint / Cannot access memory at 0x10057f64` had two causes,
both now fixed:

1. **Breakpoint insertion** — a **software** breakpoint writes `int3` into guest
   memory, but when `gdb -batch` attaches the vCPU is in **real-mode DOS**
   (between compile-loop iterations) where the PM linear page `0x10057F64`
   isn't mapped, so insertion failed.  Fix: use **hardware breakpoints**
   (`hbreak`, via DR registers) — they don't touch guest memory, arm from any
   context, and fire when the CPU reaches that linear address in PM.  `cs_base`
   (= 0x10000000) was already correct and is re-derived at runtime via QMP.
2. **Single-function extraction didn't compile** — e.g. `start_smacking` passes
   the sibling function `vgawinrout` (defined elsewhere in `smacker.c`) as a
   callback pointer → `E1011 'vgawinrout' has not been declared`.  Fix:
   `c2 regtrace` now compiles the **whole real TU** (exactly what decomp-verify
   compiles) — always compiles, and the target's codegen is byte-identical to
   the real build because prototype visibility (Rule 37) is preserved.
   Decisions span the TU; the report labels the target + function count.

**Why not dosemu2** (considered, rejected): dosemu2 is **not in nixpkgs** (only
`dosemu_fonts`); building it = a chain of source components (forked `stsp/nasm`
seg-elf + `thunk_gen` + custom i686 binutils + `fdpp` + `comcom32` + autotools),
multi-hour and fragile.  And per dosemu2's `doc/README.gdb`, `-gdb` debugs
*dosemu itself*, not the DPMI client — client debugging needs `dosdebug` or
manual segmented gdb plus knowledge of dosemu's DPMI mmap layout (its own RE
task).  The two QEMU fixes above were far cheaper and address the exact failure.

Note: `regtrace.serial.log` should show `COMPILE-EXIT 0`; wcc386 also writes
errors to `TARGET.ERR` on the run floppy (DOS stderr doesn't reach serial).

**Runtime note:** a real function pulls in `entities.h`/`c2_data.h` (~130 KB),
which wcc386 parses slowly under pure-TCG QEMU (tens of seconds) — budget a
minute or two per run.  gdb attaches *during* the (slow) first compile and
catches `GiveBestReg` in it; `RUN.BAT` also loops the compile as a safety net.

Note: the behavioural model (`regalloc-model.md`) was already proven against the
binary by black-box probing; this map + live breakpointing is for
**spot-confirming** specific decisions and reading exact `CountRegMoves` inputs,
not re-deriving the model.

## `conflict_node` struct layout (10.0a, -4r flat) — for the regtrace dumper

Derived from `cg/h/conflict.h` + `cg/h/inslist.h` + `cg/h/gbit.gh`/`lbit.gh`
and **validated against two live-confirmed anchors**: `tree@+0x10` (the working
candidate read) and `possible/class@+0x56` (the working class read).  The 0x56
anchor only lands correctly if `conflict_state` is a 2-byte enum and every
preceding field has the size below, which fixes the whole layout.

Sizes: pointer/`save_def`/`hw_reg_set`/`a_bit_set` = 4; `local_bit_set` = 4
(1×a_bit_set); `global_bit_set` = 16 (4×a_bit_set); `name_set` = 24 (regs 4 +
out_of_block 16 + within_block 4); `conflict_id` = 20 (within_block 4 +
out_of_block 16); `conflict_state` enum = 2.

| off  | field | type | notes |
|------|-------|------|-------|
| +0x00 | next_conflict | ptr | walk the list |
| +0x04 | next_for_name | ptr | |
| +0x08 | **name** | ptr (union name) | conflict identity |
| +0x0C | start_block | ptr | |
| +0x10 | **tree** | ptr (reg_tree) | ✅ anchor; `tree->regs`@tree+0x10 = candidate list |
| +0x14 | **savings** | unsigned_32 | ✅ SortConflicts/CalcSavings key |
| +0x18 | num_constrained | int | |
| +0x1C | available | int | |
| +0x20 | with | name_set (24) | regs+out_of_block+within_block |
| +0x38 | **ins_range.first** | ptr (instruction) | live-range start → source line |
| +0x3C | ins_range.last | ptr (instruction) | |
| +0x40 | id | conflict_id (20) | |
| +0x54 | state | conflict_state (2) | |
| +0x56 | **possible** | byte | ✅ anchor; aka reg_set_index = "class" |

`reg_tree` (cg/h/conflict.h): lo,hi,temp,alt (4 ptrs) then **regs@+0x10**,
chosen@+0x14 (hw_reg_set), size@+0x18, offset@+0x1C, idx@+0x20, has_name@+0x21.

`ins_header` (cg/h/inslist.h): prev@+0x00, next@+0x04, live (name_set 24)@+0x08,
**line_num@+0x20** (source_line_number = unsigned_32), opcode/state after.  So
`conflict → +0x38 (ins_range.first) → +0x20` gives the `-d1` source line of the
value's live-range start.

These offsets back the **Phase 1 regtrace dumper**: at GiveBestReg (eax =
conflict being assigned) read savings/name/line and attribute by line range.
Future phases (instruction-list / IR dumps) can reuse `ins_range` + `head` here.

## Variable names + source line (front-end symbol resolution)

A register-allocation `conflict_node`'s value is `conflict->name` (`+0x08`),
a `union name`.  For a user variable it is `N_TEMP`/`N_MEMORY` (class byte at
`name+0x04`) carrying a **front-end symbol handle** `v.symbol` at **`name+0x14`**
(16-bit handle; `0` for anonymous compiler temps).  `name_def` head is:
`next_name@+0x00, class(byte)@+0x04, name_class(byte)@+0x05, size@+0x08`;
`var_name` adds `conflict@+0x0c, offset@+0x10, symbol(handle)@+0x14`.

The handle resolves to a name via the front-end (linked into the same wcc386
image): `FEName(handle) { if(!h) return "*** NULL ***"; return SymGetPtr(h)->name; }`.

Located by static RE (call graph is valid in the file: flat image, fixed base
0x10000000, no ASLR, so intra-app `call rel32` needs no fixup):

| app-offset | symbol | notes |
|---|---|---|
| `0xf2c6` | **`FEName(handle16) -> char*`** | `test ax,ax; jne; mov eax,0x706fb("*** NULL ***"); ret; movzx eax,ax; call SymGetPtr; mov eax,[eax]; ret` |
| `0x1932f` | **`SymGetPtr(handle) -> SYMPTR`** | handle->symbol-table pointer (CurFuncHandle / PCH_SymArray / SymAccess cache) |
| `0x706fb` | `"*** NULL ***"` string | (data app-offset; data FOFF = file-0x2200, code FOFF = file-0x1200) |

`SYM_ENTRY` (front-end, `cc/h/ctypes.h`): `char *name@+0x00`, then `sym_type`,
`handle`, `defn_file_index` (file), `d.defn_line` (line).  So `SymGetPtr(handle)`
yields name + file + line in one shot -- the actionable per-variable attribution.

The hook (mkhook.py) calls `FEName(handle)` between `pushad`/`popad` (so the
displaced GiveBestReg prologue resumes with the right register state; __watcall
preserves EDI/ESI/EBX/EBP across the call) and copies 20 bytes of the name
string into the trace record.  `c2 regtrace` then prints
`variable | savings | chosen | candidates` per conflict, filtered to the target
function by the LINE_LO/LINE_HI source-line globals.

## Hook code space — caves, chaining, and image extension (2026-06-01)

The GiveBestReg hook lives in zero-padding **caves** inside the mapped flat
image (the whole TNT payload maps RWX at linear `0x10000000`; no NX on the 386,
so both code- and data-segment zero-runs are executable).  Two facts make space
a non-issue in practice:

* **Data is unlimited.**  Trace records stream to `B:\TRACE.BIN` via INT 21h —
  not to memory — so record size / count never competes for cave space.  Only
  hook *code* uses caves.
* **Code is cave-chained.**  `mkhook.py` splits the stub into jmp-linked
  CHUNKS, one per cave (`CAVES[]`).  Registers + the on-stack record buffer
  persist across the inter-chunk `jmp`; each chunk's `.`-local branches stay
  within its cave (the split point is the `.nostr` funnel).  Current stub:
  chunk0 162/272 b @ `0x1ADD5`, chunk1 89/250 b @ `0x19E67`.

**Cave inventory** (largest zero-runs ≥ 64 b; `app = file − 0x1200`; `refs_into`
= count of code disp32 pointing inside → 0 means pure padding, safe):

| app-off  | len | region | refs_into | note |
|---------:|----:|--------|----------:|------|
| `0x078C29`| 863 | data | 6  | largest; data-seg (verify before code use) |
| `0x079DB5`| 399 | data | 0  | safe; in `CAVES` |
| `0x01ADD5`| 272 | code | 1  | primary (known-good); `CAVES[0]` |
| `0x019E67`| 250 | code | 0  | safe; `CAVES[1]` |
| `0x02B5C3`| 250 | code | 0  | safe; `CAVES[2]` |
| `0x021D26`| 266 | code | 3  | |

Total zero-run bytes ≥ 64: **~7 KB**.  Adding a cave = append its
`(app_offset, capacity)` to `CAVES[]` (and a chunk to `_CHUNKS`); `patch_image`
asserts each is still zero in the exact build before overwriting.  ~7 KB is far
more than any foreseeable hook (the full stub incl name resolution is ~250 b).

**Image extension (deferred).**  The LX header at file `0xC08` maps only the
~37 KB TNT *bootstrap* (3 objects at bases `0x10000/0x20000/0x30000`); the
540 KB compiler payload is flat-mapped separately by the extender at
`0x10000000`.  Growing that mapping = Phar Lap TNT flat-image header surgery
(find the load-size/BSS fields the bootstrap reads) — multi-session with
miscompile risk, and unnecessary while caves + the INT-21h record file cover
the need.  Revisit only if a single hook ever needs > ~7 KB of *code*.

## CountRegMoves — the selection tie-break (modelling, in progress)

`GiveBestReg` (cg/c/regalloc.c) picks among the free, non-`TooGreedy`
candidates the one with **max `CountRegMoves`**; ties break by `GivenRegisters`
(prefer a register already used in the function) then candidate order:

```
best=EMPTY; best_saves=-1
for reg in tree->regs:                       # DoubleRegs order (now fully captured)
    if reg not in conf->with.regs and reg not in except and not TooGreedy(...):
        saves = CountRegMoves(conf, reg, conf->tree, 3)
        if saves > best_saves or (saves==best_saves and reg in GivenRegisters and best not in):
            best=reg; best_saves=saves
```

The greedy `_chosen_reg` (first free candidate) is exactly the
**CountRegMoves≡0** case — validated fully self-consistent on pm_map0.c
(`regalloc-predict-live.py`).  CountRegMoves only overrides it when assigning a
*later* candidate would turn a `MOV Rn=>Rn` (full move, +`tree->size`) or a
commutative `OP Rn,x=>Rn` (+`tree->size/2`, ops ADD/MUL/AND/OR/XOR on 386) into
a no-op, by walking the conflict's `ins_range` and matching `tree->temp`/`alt`
against each instruction's operands/result.

**Substrate captured (validated, codegen-neutral — read-only):** per conflict
the hook now dumps `ins_range.first/last` (conf+0x38/+0x3C), the
`head.next`-walked range length (capped 64; loop-spanning values like the
counter/accumulator hit the cap — expected), and `tree->temp`/`tree->alt`
(reg_tree+0x8/+0xC, sane name-arena pointers).  Record grew 96→116 b; the walk
loop pushed chunk0 to 211/272 b (cave-chaining absorbs further growth).

**Computing CountRegMoves — DONE.**  The `instruction` struct offsets were
pinned + validated (next section), the full `ins_range` is walked capturing
`(opcode, result, op0, op1)` plus each operand's register (if N_REGISTER), and
`regalloc-predict-live.py` computes CountRegMoves + the full GiveBestReg
selection over `ins_walk`.  Validated by the model resolving the greedy gap
(ECX) — see "Validation status" below.

## `instruction` struct offsets — PINNED + validated (2026-06-01, 448/448)

Bisected by capturing a raw 80-byte window of `conf->ins_range.first` and
matching `tree->temp` (the first instruction in a conflict's range is the
value's definition, so `result == tree->temp`):

| field | offset | notes |
|-------|-------:|-------|
| `head.prev` / `head.next` | +0x00 / +0x04 | instruction* (next = range walk) |
| `head.live` | +0x08 | name_set (24 b) |
| **`opcode`** | **+0x22** | byte; **OP_MOV = 0x26** |
| `state` | +0x23 | byte (NEEDS_WORK=0 / OPERANDS_NEED_WORK=1 / READY=2) |
| `table`/`u`/`zap` | +0x24/+0x28/+0x2c | opcode_entry* / gen_table* / register_name* |
| **`result`** | **+0x30** | union name* — == `tree->temp` in 448/448 |
| `id` | +0x34 | int |
| **`num_operands`** | **+0x3f** | byte |
| **`operands[0]`** | **+0x44** | union name* |
| **`operands[1]`** | **+0x48** | union name* (commutative 2nd operand) |

**Opcode encoding:** the source enum's high values are shifted by
target-`#include`s (so OP_MOV is 0x26, not the source's 53), but the **low
binary opcodes are unshifted** and CountRegMoves needs only those: OP_ADD=0x04,
OP_EXT_ADD=0x05, OP_MUL=0x08, OP_AND=0x0d, OP_OR=0x0e, OP_XOR=0x0f, plus
OP_MOV=0x26.  Confirmed: 0x26 is the only high-frequency single-operand op
(240/448, all num_operands==1); OP_AND=0x0d matches source.

The hook walks the **whole** `ins_range` (capped INS_CAP=16) and captures
`(opcode, result, op0, op1)` per instruction (`ins_walk[]` in regtrace.json);
`ins_walk[0].result == tree_temp` in 448/448 (the first ins is the def).  The
3-chunk cave-chained stub (185/91/92 b across three caves) absorbed this growth
with room to spare.

**CountRegMoves input — COMPLETE (2026-06-01).**  The walk now also derefs
each operand: if `name->class@+0x04 == N_REGISTER(3)` it reads the hw_reg_set at
`register_name.reg@+0x0C` (else 0), captured as `result_reg`/`op0_reg`/`op1_reg`
in `ins_walk[]`.  Validated: 448 records, GP registers correctly identified
(EAX/EDX/EBX/ECX/ESI/EDI/EBP).  TWO crash fixes were needed: (1) gate operand
derefs by `num_operands@+0x3f` and range-gate every pointer (0x10000..0x200000)
— reading garbage operand slots faulted the compiler; (2) keep all hook code in
**code-region** caves — the data-region cave (0x79DB5) is NOT executable under
TNT paging (running the file-write chunk there gave COMPILE-EXIT 1).  Offline,
filter `*_reg` to the known GP hw_reg_set encodings (byte/word/FP regs and rare
class==3 false positives otherwise appear as OTHER).

The 4-chunk cave-chained stub (128/136/91/92 b across four code caves) now
carries the entire CountRegMoves substrate.  The offline count is a pure
function over `ins_walk`: for candidate GP reg R, sum over instructions where
one side (result/op0/op1) is `tree_temp`/`tree_alt` and another side's `*_reg`
== R — MOV(0x26) → +`tree->size`, commutative (ADD 0x04/MUL 0x08/AND 0x0d/OR
0x0e/XOR 0x0f) → +half.  Was: the per-register AllocRegName map.  CountRegMoves scores a candidate
`reg` by counting `ins_walk` instructions where one side (`result` / `op0` /
`op1`) is `tree->temp`/`alt` and the *other* side is `AllocRegName(reg)` (an
operand already fixed to register `reg`): MOV → +`tree->size`, commutative
ADD/MUL/AND/OR/XOR → +half.  We have the full walk + the temp/alt names; the
only missing map is name-pointer → physical register.  Capture it once (the 7
register names are stable globals; read each operand's `class@+0x04`==N_REGISTER
and its `reg` field, or snapshot `AllocRegName` results) and the offline
CountRegMoves becomes a pure table lookup over `ins_walk`.

## Validation status (factual, 2026-06-01)

What is captured live and proven, vs what is modelled, vs what is blocked:

* **Captured from the real compiler** (`c2 regtrace`, hooked `GiveBestReg`):
  per conflict — `savings`, `with.regs` (interference), the full 8-entry
  candidate list (DoubleRegs order), variable name + def line, the conflict's
  `ins_range`, and a per-instruction walk of that range with each operand's
  register.  All offsets validated against the live image (`result == tree_temp`
  448/448; GP registers correctly decoded).

* **Modelled offline** (`regalloc-predict-live.py`): the greedy pick
  (first free candidate = CountRegMoves≡0 case) and the full `GiveBestReg`
  selection (max CountRegMoves, candidate-order tie-break).  `c2 regtrace`
  surfaces both (`greedy` / `CRM` columns) with the per-candidate scores.

* **Evidence the model is correct** (not assertion):
  1. *Self-consistency* — every register appearing in any conflict's
     `with.regs` is reproduced as the model's chosen for some conflict
     (93/93, all 7 GP regs incl EBP) on the pm_map0.c TU.
  2. *CountRegMoves closes a real gap* — the greedy model alone leaves ECX
     "unexplained"; the full CountRegMoves model picks ECX for `front_offset`
     (score 4), the only thing that explains it.
  3. *End-to-end disasm check* (`regalloc-predict-live.py end_to_end`,
     automated) — the full `give_best_reg` model predicts the register each
     named variable ACTUALLY gets in our compiler's output: `get_pm_from_actual`
     col=EDX, pm_val=EAX, row=ECX — **3/3 match**.  This check also *caught and
     fixed* two model bugs, which is the point of having it:
     - CountRegMoves is unreliable when `range_len >= INS_CAP` (16) because the
       `ins_walk` is truncated; the model falls back to greedy for those
       loop-spanning ranges.
     - **The "last GiveBestReg sighting sticks" assumption was wrong.**  RegAlloc
       re-presents a conflict across passes; col's actual EDX matches its
       *first* sighting (only EAX taken), not the later higher-savings
       re-presentation (EAX+EDX taken → EBX).  Both `regalloc-predict-live.py`
       and the `c2 regtrace` report now keep the FIRST sighting.

* **Blocked**: capturing the *actual* chosen register live (per-conflict, to
  replace the disasm cross-check with a direct equality check).  The
  AssignConflicts driver that calls `GiveBestReg` runs across a Phar Lap TNT
  segment boundary (its runtime cs-offset is not a clean uniform shift from its
  file/app-offset), and `eax` at the post-call site `0x58D4B` is not cleanly the
  returned register.  The hook is implemented but guarded off
  (`ENABLE_CHOSEN_HOOK=False`); the harness/RUN.BAT merge plumbing is in place
  for when the driver's segment layout + return-value register are RE'd.

## Chosen-register live capture — status & the stale-binary guard (2026-06-01)

**Infrastructure works; the value isn't exposed by this binary.**  The capture
splices GiveBestReg's epilogue (0x58B6F, proven +0) and fires cleanly for all
448 conflicts with no crash.  But this 1994 build does NOT surface the chosen
register as a clean `hw_reg_set` at any single hookable point:

  * The driver's GBR-return site (where the 5y-newer OW source would have
    `given` in eax) is at file 0x58D4B+0x1200, which maps to cs 0x158D4B — a real
    file↔cs discontinuity; splicing it lands the jmp at cave+0x100000 and faults.
  * At the driver return eax==0 (proven: an 8-byte capture there gave given==0
    for all 2331 calls) — this build returns the result differently from the
    newer source.
  * GBR applies the assignment via FixInstructions directly to the instruction
    operands; the conflict node is REWRITTEN by the epilogue (with.regs bits
    cleared at conf+0x1c) with no clean register field surviving in conf[0..0x30].

So the chosen register lives only in the rewritten `ins_range` operands;
extracting it needs a post-rewrite operand walk (a further RE layer).  The
predictor is validated WITHOUT it — 3/3 vs the actual compiled disasm
(`get_pm_from_actual`) plus full self-consistency — so the hook is left OFF
(`ENABLE_CHOSEN_HOOK=False`) rather than shipping a misleading 0.

**Stale-binary guard (the recurring failure mode).**  Several debugging hours
were lost to the harness silently running an OLD hooked `WCC386H.EXE`: when the
stub overflowed its cave, `patch_image` raised, the deploy was skipped, and the
*previous* stub kept running (fault eip frozen at the old 0x2C4FD regardless of
edits).  `mkhook.ensure_in_cimg` is now hardened so this cannot happen:

  1. `verify_src_clean()` — the source must be the pristine unhooked wcc386
     (intact GiveBestReg prologue + all caves still zero); an accidental
     in-place patch is rejected up front.
  2. `patch_image` raising (cave overflow, bad source) propagates — the caller
     aborts instead of running whatever is already in the image.
  3. After mcopy, the deployed bytes are **read back and byte-compared** to the
     freshly-patched image; any mismatch raises with the `hook_fingerprint()`.
     The run only proceeds on a proven byte-for-byte match.

NB: never `rm` `cache/c.img` — it is the persistent toolchain HDD, not a build
artifact; `ensure_in_cimg` re-bakes `WCC386H.EXE` into it idempotently.  Deleting
it forces a full `mktoolchain.sh` rebuild.

## CG opcode enum (1994 wcc386) — behaviorally decoded (2026-06-01)

The 1994 binary's CG opcode enum was recovered by tracing isolated
one-operation probe functions through the hooked compiler (`int p_sub(int a,
int b){return a-b;}` etc., one op per function, spaced so the per-function
`line_lo/line_hi` brackets don't overlap; read the opcode of each value's
defining instruction).  **The low integer ops match the Open Watcom source
enum exactly**; MOV and the compare block are shifted down because the 1994
build has fewer float/intrinsic ops than the 5y-newer OW source.

This corrected a real bug: the prior `_OP_COMMUTATIVE = {0x04,0x05,0x08,0x0d,
0x0e,0x0f}` (a wrong opcode assumption) made `CountRegMoves` treat LSHIFT/MOD/
EXT_SUB as commutative.  The fix (`{0x01,0x02,0x05,0x06,0x09,0x0a,0x0b}` =
ADD/EXT_ADD/MUL/EXT_MUL/AND/OR/XOR) cut spurious greedy-overrides 9→2 on
`get_pm_from_actual` while keeping the end-to-end 3/3 + self-consistency.

| opcode | name | operand shape | how confirmed |
|-------:|------|---------------|---------------|
| 0x01 | ADD | R,o0,o1 | `a+b` |
| 0x02 | EXT_ADD | R,o0,o1 | (source-adjacent; extended add) |
| 0x03 | SUB | R,o0,o1 | `a-b` |
| 0x05 | MUL | R,o0,o1 | `a*b` |
| 0x07 | DIV | — | `a/b` (usually a runtime call) |
| 0x08 | MOD | — | `a%b` (runtime call) |
| 0x09 | AND | R,o0,o1 | `a&b` |
| 0x0a | OR | R,o0,o1 | `a\|b` |
| 0x0b | XOR | R,o0,o1 | `a^b` |
| 0x0c | RSHIFT | R,o0,o1 | `a>>b` |
| 0x0d | LSHIFT | R,o0,o1 | `a<<b` |
| 0x11 | NEG | R,o0 | `-a` |
| 0x12 | COMPLEMENT | R,o0 | `~a` |
| 0x24 | CONVERT | R,o0 | `(short)a` / widen / bool→int |
| 0x26 | MOV | R,o0 | self-move (result==tree_temp), 448/448 |
| 0x30-0x35 | CMP_EQ/NE/GT/LE/LT/GE | R,o0,o1 | `a==b`→0x30, `a<b`→0x34 |

## Large-TU trace truncation — root-caused + fixed (2026-06-01)

Symptom: on map.c (6604 lines) the trace's `def_line_num` capped at ~4436 and
functions past it (e.g. `get_ptr_to_corner` @5642) got MIS-ATTRIBUTED conflicts.
It looked like a line-number-field limit — it was NOT.

**Root cause: the output medium filled up.**  The hook streamed records to the
1.44 MB B: **floppy** (`run.img`), which hit 0 bytes free at ~1.03 MB
(`trace.bin` = 1,030,144 b = 1813 records × 568 b).  Once full, the INT-21h
appends silently failed, so only the FIRST ~1813 conflicts (the low-line
functions) were ever written — hence the apparent line cap.  map.c needs ~2900
conflicts; action.c (250 functions) needs far more.

**Fix:** a dedicated **writable output HDD (guest D:)**, `build_out_disk()` in
`harness.py` — a fresh 64 MB partitioned FAT16 image per run, attached at
`if=ide,index=1` (no `snapshot`, so the host reads it back; the toolchain C: is
still `snapshot=on` read-only).  The hook now writes `D:\TRACE.BIN` /
`D:\CHOSEN.BIN`.  After the fix, map.c traces **2904 conflicts**, `def_line_num`
reaches **6596**, `get_ptr_to_corner` attributes correctly, and `--explain`
gives the right lever (use-order / Rule 28a, matching the function's own source
comment) with NO `UNRELIABLE` banner.  The `_attribution_reliable` guard remains
as a backstop but no longer fires for in-range large-TU functions.
